# Changelog

What each release turned out to mean. The [roadmap](README.md#roadmap) says what is planned and what is done; this file says what was learned doing it — the boundaries that moved, the claims that were corrected, and the things that could not be done honestly.

Entries are written after the fact, from merged work.

**These versions are git tags marking milestones, not package releases.** `pyproject.toml` deliberately stays at `0.0.1`: nothing is published, and [installable distribution](README.md#roadmap) is an M5 item. A tag says "this milestone is done and here is what it meant" — it does not say the contract is stable. The fact, receipt, and IR contracts are v0 and may break until v1.0.

## Unreleased — M5

**Rule studio.** A second surface on the demo server (`/rules`) for the rules rather than the documents: every pack rendered as one decision-table grid per concluded attribute, editable as cells, rule forms or YAML, with the kernel's validator, the pack's declared `expected.yaml` cases, an ad-hoc case built by changing input values, golden-corpus impact analysis and the solver all running over one in-memory draft. Drafts are session-only and never written into `rulepacks/` — the same rule as the golden-case export, for the same reason.

*The composition was the contribution, not the tooling.* M4's exit criterion — a domain author can create, validate, test, and impact-assess a rule change without touching the kernel — was already met, by five separate command-line tools an author had to know existed. Putting them in one rail, in the order that catches things, is what let two of them visibly disagree: change New York's 45-day minimum to 60 and all four declared cases pass while the corpus reports one flipped decision. "Declared outcomes catch a pack that breaks, only the corpus catches a pack whose meaning moved" was already written down; the studio is where you watch it happen.

*Building an editor found a third half of a rule pack.* The architecture doc had carefully separated the pack's **deciding** half (hashed, frozen, replayed) from its **speaking** half (phrasing, deliberately never hashed). Neither accounts for the prose: `DEMO-SYNTHETIC` on an invented window, `TODO(verify)` naming what was unconfirmed, the `MODELING BOUNDARY` header, the comment saying whether an `overrides` is a legal exception or a workaround. Strip every comment from a pack and validation passes, all 351 receipts replay byte-for-byte, and impact reports zero — the honest-labeling invariant lives entirely in a layer nothing checks. Any tool that re-emits a pack from the IR destroys it while leaving both governed halves provably intact. The response was neither to forbid the re-emission nor to call it lossless: the studio shows a normalised diff for *what you changed* beside the raw file diff for *what you would be committing*, and keeps a text path that preserves comments.

*One silent bug, found by the round-trip guard rather than by a test.* `duly_dmn.emit.emit_pack` emitted a fixed `pack`/`decisions`/`rules` allow-list — correct for every pack the compiler produces, and silently lossy for a hand-written one, dropping `abstentionPolicy` and `calendars`. A draft missing an abstention policy validates, adjudicates, and answers differently. It now emits every top-level key in input order, handles floats (a quoted `"0.9"` confidence floor is a string the kernel rejects), and the studio asserts `yaml.safe_load(emit(pack)) == pack` before storing any draft. The DMN compilation is byte-unchanged.

Also: `impact.analyze` gained `pack_overrides`, so a candidate pack that exists only in memory can be measured against the corpus — an impact number the author sees *before* writing the file is the only one that can change their mind. `emit_pack` gained a `header` parameter so a non-DMN generator can say how it generated a pack, with a test that a replaced header moves no byte of the body.

**Evidence browser.** A surface on the demo server (`/evidence`) for the evidence rather than the answer: every document a case holds — the committed source bytes beside the extractor's rendition — and every fact ever asserted about it, each with its grounding, provenance, confidence method and calibration reference, content hash, ontology slot, supersession chain, and which of the pack's questions cite it. Above all of it, a knowledge-time dial whose stops are the moments the case's knowledge actually changed.

*The store had been bitemporal since M2 and nothing showed it.* The decision workspace shows the facts a receipt cited — the right frame for reading a decision, and one that structurally cannot show a fact no rule needed or a fact that is no longer true. Dragging the dial back past a reviewer's correction makes the corrected fact not-yet-known, returns the below-floor machine fact it superseded to live, and moves the citations with them. Nothing new is stored to make that work; it is the same event log projected at a different horizon, which is the point.

*Immutability is usually defended as preservation, and preservation is the weaker half.* An append-only log admits two queries: *which facts bind at this horizon* — what adjudication needs, and what `as_of` answers — and *what became of this fact*, which adjudication never asks and an auditor asks first. A mutating store answers neither honestly; a store with a deletion-free log and only a survivor projection answers the first and merely promises the second, which is where duly had been. "Nothing is lost" becomes checkable at the point something reads the history back, not in the schema, which a system can satisfy perfectly while remaining unable to say what it used to believe. So the browser recomputes liveness from the log rather than calling `as_of`, and a test walks every case at every point on its timeline requiring the two projections to agree — a differential check, in the same spirit as `prove` standing behind the pack validator. One implementation answering both questions would have proved nothing.

*The document turned out to have two faces, and only one of them can carry a highlight.* A fact's grounding cites the source document's SHA-256 — the bytes — and a character span into a *rendition*, one extractor's reading of those bytes. The browser serves both and reports whether the file on disk still hashes to what the facts cite, but it draws spans only on the rendition: character offsets are not page coordinates, and an overlay computed from them would be a guess wearing the costume of provenance. The same discipline covers two facts quoting overlapping text — the browser names the span it could not draw instead of dropping it. `Rendition` is now a row in the architecture doc's artifact table, which it should have been all along.

*One refusal and one gap, both stated rather than papered over.* Without the session fact store there is no event log, so the timeline is reported as *absent* rather than rendered with a single stop implying knowledge never changed. And a fact retracted without replacement is unreachable from any live fact through the store's public API, so it does not appear — nothing in the demo retracts, and reaching around the API would have been the worse trade.

**Receipt viewer.** A surface on the demo server (`/receipt`) for a receipt that already exists: the 351 committed receipts searchable by case id or hash from a picker in the toolbar, any receipt openable by paste or file, rendered as the kernel's own audit report and re-verified on open — its own hash, each pinned fact's content hash, and a full re-adjudication compared byte-for-byte. `duly_kernel.report` gained a third renderer over the section structure the Markdown and PDF already share, so the browser is a new *walk* rather than a second report.

*The corpus proved 351 receipts replay; nobody outside this repository could check one.* That gap is what the viewer closes, and closing it sharpened a claim the architecture doc had been making loosely. Content addressing was described as "mutation is detectable" — true relative to a seal that whoever mutated the document can re-apply. Flip a verdict, recompute `receiptSha256`, and the artifact is consistent again: genuine facts, correct hashes, a well-formed derivation, a report rendering fluent sentences over real statutory citations. Every check that treats the receipt *as a document* passes. Only re-running the rules refuses it. So tamper-evidence and fidelity are different properties, verification is three checks reported separately rather than one verdict, and the middle check must be able to say *not checked* — a receipt pins facts by hash, so one arriving alone genuinely cannot reproduce its own evidence, and passing it would convert an absence into an assurance.

*The second distinction is about standing, not computation.* Golden replay and single-receipt verification run the same kernel over the same inputs and compare the same bytes. What differs is who may conclude something: replay over the corpus is a claim duly makes about artifacts duly produced, checked by CI duly configured. The identical computation, performed by the party holding a receipt against the facts and pack version it names, needs no trust in the producer. A decision record only its author can verify is documentation; one its recipient can verify is a receipt.

*A bug the API tests could not see.* `/inspect` first took receipts and facts as JSON objects, and every genuine fact came back reported as tampered with — only through a real browser. JavaScript has one number type, so a fact's `"score": 1.0` survives `JSON.parse`/`JSON.stringify` as `1`: a different canonical body, a different content hash. Python round-trips it faithfully, which is exactly why a Python-side test suite proved nothing. Content addressing is over bytes, so the endpoint now takes raw JSON *text* and Python does the only parse. Any future surface moving hashed bytes through a browser inherits this.

*One refusal worth naming.* When a receipt's `rulePack.version` no longer matches the file on disk, the viewer does not fall back to it. Rule descriptions from a version the receipt never saw would read as the text its rules carried; the gap is reported as `pack-moved` with both versions, and the rule text is omitted.

**Version scopes.** The receipt's `engine.version` — inside every receipt hash — was `duly_kernel.__version__` by direct import, which made the golden corpus a hostage to the release cadence: publishing the distribution under any new number would have invalidated all 351 receipts without a rule, a fact, or a decision having changed. It is now a pinned constant, `SEMANTICS_VERSION`, naming the kernel's *decision semantics*. The emitted bytes are unchanged; what changed is the dependency.

*Three scopes, nested one way only, and a coincidence that hides the regression.* The distribution moves on any release, the kernel package moves when its code changes, and the semantics version moves when its meaning changes — a semantics change implies a code change implies a release, never the reverse. All three read `0.0.1` today, so re-coupling the sealed field to the package version changes no output, passes every test, and replays the corpus green — until the first release breaks 351 receipts at once, far from the edit that caused it. The guard is therefore behavioural: a test bumps the package version to `1.0.0` and requires a byte-identical receipt. The sealed value is a handle, not a claim, for the same reason `NY-NR-45` keeps its name.

*The procedure got written down where it cannot be missed.* [docs/release-process.md](docs/release-process.md): the version declarations across four scopes and which move for a given change, what counts as breaking per contract — including that the receipt hash covers the whole body, so "additive and backward-compatible" does not exist for receipts — and the discriminator that keeps a semantics rev honest: golden bytes moved with packs and facts unchanged means the kernel's meaning moved. Three decisions are marked PENDING rather than guessed; they resolve in M5's compatibility policy.

**Consumed from outside.** [`examples/minimal-integration`](examples/minimal-integration/) is the whole contract at its smallest: a fictional company's expense policy as its own ontology and its own two-rule-plus-constant pack, three facts, one adjudication, one receipt verified by recomputing its hash — about a hundred lines, none of which import a path inside duly. `check_wheel.sh` builds a wheel, installs it into a clean virtualenv, copies the example somewhere else entirely, and runs it with the source tree off `sys.path`.

*A test that passes inside a repository cannot distinguish a toolkit from a repository with a library-shaped subdirectory.* Inside the checkout every assumption about where files live happens to be true, which is why the example is an instrument and not only a deliverable. Running it from a wheel found four things no suite here could see: content addressing — the first call any integration makes — reachable only as `duly_kernel.receipt`, a module path that reads private; the conformance CLI defaulting `--ontologies` to duly's own directory and raising a traceback rather than a diagnosis when that is wrong; `verify` and `impact` disagreeing about an empty corpus, so an adopter's first CI run fails on the second command they try; and a kernel-only `pip install duly` pulling in a web framework and a PDF library. The committed `receipt.json` is diffed against what the wheel produces, so it proves determinism across *environments* rather than only across runs.

*The gap was wider than the example could reach.* It exercises two packages of nine, so [`.github/scripts/wheel_smoke.py`](.github/scripts/wheel_smoke.py) now touches one real entry point per shipped package from an installed wheel — and immediately found that `duly_review` did not work at all outside this repository. The queue read the grounded-fact schema from a path relative to the *repository*, and `spec/` is in no wheel, so its central operation raised `FileNotFoundError` for every adopter while every test here passed. Known failures in that script are declared with the finding that owns them and fail the run if they start passing, so an entry cannot outlive its bug; fixing that one emptied the list.

*A threshold is a rule, not a number in a guard.* Writing the example's `$200` limit found that the IR has no money literal — money is an amount *and* a currency, and a bare number is only the first — so the limit became its own cited, effective-dated rule bound with `derived:`. That is the better artifact and it is what every committed pack already does: no `when:` guard in this repository contains an inline numeric literal. Chasing it found a real bug in the other direction. A DMN cell reading `> 200` against a money column is the most natural thing a business analyst writes; it is valid S-FEEL, renders to valid duly source, and produces a pack `validate_pack` *accepts*, because the rule IR type-checks nothing at load time. The compiler reported success and the pack died on the first real fact. Given the pinned ontology's value kinds it now refuses that cell by name — but the underlying gap, that pack validation does not type-check expressions at all, is recorded as [rule-IR open question 4](spec/rule-ir.md#open-questions-v0) rather than papered over.

**One canonical form.** `content_hash` was implemented **seven times** across the repository under three signatures, two of them carrying comments reading "must match spec/validate.py exactly" — a copy pinned by a code comment. They are now one implementation in [`duly_core`](core/duly_core/), whose charter is stated in its docstring and deliberately narrow.

*Copies of a function are not independent implementations.* The plan of record had been to keep the seven and add a test asserting they agree. duly's real differential checks compare different *mechanisms* — `prove`'s SMT solving against `validate_pack`'s syntactic matching, the evidence browser's log replay against the store's survivor projection — and seven copies of three identical lines have no algorithmic diversity at all. Such a test proves only that nobody typed it wrong, while borrowing the credibility of a check that does much more, and it crowds out the one that would work.

*The oracle for a canonicalization function is a specification.* [`spec/canonical-vectors.json`](spec/canonical-vectors.json) commits eleven `(document, canonical bytes, digest)` triples, and the property tests re-derive what RFC 8785 requires *independently* of the implementation. Which resolved a claim the schemas had been making loosely: RFC 8785 orders object keys by UTF-16 code unit, Python's `sort_keys` orders by code point, and the two disagree above the BMP. duly said "RFC 8785" and implemented the approximation. Across 1772 committed documents zero have a non-ASCII object key, so implementing the real rule was provably inert — 351 receipts replay byte-for-byte with the sort order changed — and the label became true rather than being weakened. The vectors are also the artifact another language needs: implementing duly's fact contract previously meant working from prose.

*The contract ships.* The three JSON Schemas moved from `spec/` into `duly_core`, because a path relative to a *package* resolves identically in a checkout and in site-packages while a path relative to the *repository* resolves in exactly one of them. Moved rather than copied: two shipped packages read them, and vendoring into one would have recreated the defect `duly_core` exists to remove. That widened a charter written a week earlier as "nothing else, ever" — the amendment and its reasoning sit in the docstring, so the next widening has to argue with a stated position rather than an absence.

**The seams that assumed a repository.** Each toolkit package now takes the paths it reads from its caller. `duly_conformance`'s CLI has no path default at all — pass `--ontologies` or set `DULY_ONTOLOGIES`, and a registry that cannot be loaded is diagnosed with an exit code rather than raised as a stack trace, kept distinct from the exit code for "your facts are wrong" so a CI job can tell a broken registry from a broken corpus. `verify`, `impact` and `generate` shared out three different answers to "what is a case's pack path relative to?" — two of them resolved against duly's own install location — and now share one that tries the working directory and the corpus's parent, naming every candidate when nothing resolves.

*An empty corpus is a state, not a mistake.* `verify` returned 0 on one and `impact` raised, so the two disagreed about identical input. Both now succeed, and both say in words that nothing was measured, because "0 of 0 decisions flip" and "verified 0 cases" are true sentences that read as passes — the trap [rulepacks/README.md](rulepacks/README.md) already documents one level down for a pack with no corpus coverage. A *missing* directory still fails.

*The corpus generator's templates are example content, and the generator is not.* The six packs, their vocabularies, and the fact builders that speak them are teaching artifacts; the scheduling, seeding, validation and writing around them are the toolkit. `register_kind` and `register_template` make that a seam an adopter can populate for their own packs, and refuse a duplicate name rather than overwriting — a corpus whose contents depend on import order is not reproducible, which is the one property that file exists to provide. The refactor was proved inert by regenerating at the same seed and diffing bytes, and that check immediately caught a transcribed default question that changed 17 cases while the full suite, replay *and* impact analysis all stayed green: the generator had faithfully produced 350 valid cases of the wrong thing.

## v0.4.0 — M4: standards, authoring, and static assurance

Ten capabilities across twenty-five pull requests (#6–#30), and **the golden corpus was never regenerated once**. All 351 receipts still replay byte-for-byte from before any of it. Every track's acceptance test was that `git diff -- golden/` came back empty.

### Interchange and contract

**PROV-O JSON-LD export.** Facts, receipts, and run envelopes expand to W3C PROV triples under external context files, stored bytes unchanged. The mapping is deliberately partial — bitemporal effective time, confidence, and abstentions have no faithful PROV equivalent and stay in duly's namespace. An earlier "lossless mapping" claim was corrected in the process.

**Ontology conformance gate.** A fact's `schemaRef` resolves against a registry of versioned, immutable LinkML artifacts; a misspelled attribute that previously surfaced only as a rule silently failing to bind now fails ingestion loudly. The hot-path validator interprets a documented LinkML subset rather than importing linkml-runtime, which would drag RDF tooling into the runtime; a marker-gated suite proves the files are genuine LinkML under real tooling.

**Pack-embedded calendars.** `add_business_days` walks a calendar carried inside the rule pack — excluded weekdays, cited holiday dates, and a coverage window that raises rather than guessing past its edge. "Last Monday in May" became legal content, versioned and receipt-pinned with the rules that use it, instead of engine code. The TILA pack now computes the rescission deadline it could previously only certify.

### Authoring

**DMN decision-table compiler.** DMN 1.3+ tables compile into the rule IR; the kernel cannot tell the result from a hand-written pack. Deliberately narrow — S-FEEL cells only, three of seven hit policies, a mandatory citation and effective date on every row. It refuses rather than approximates: an uncited row is a compile error, not an invented `TODO(verify)`.

*The acceptance criterion was unachievable as written.* It demanded a DMN-authored pack produce "the same decision **and receipt**" as its IR equivalent. A receipt pins its pack's name and version, so two packs are two identities and the hashes cannot match. What is proven instead — same decision, same rules fired in the same order, same defeat chains, same input facts — is asserted alongside the difference, which a test pins as precisely as the agreement.

*And the proof is fixture-bounded.* Perturbing a compiled rule from `> disclosed` to `>= disclosed` leaves the whole equivalence suite green, because the two differ only when the amounts are exactly equal and no committed fixture reaches that boundary. A perturbation the fixtures can see fails 10 of 12 tests. This is what motivated pack equivalence in the verifier below.

**Pack-owned decision phrasing.** A decision's verdict wording moved from `demo/app.py` into the pack, alongside the `question` a pack already declared. Every determination the demo can render is byte-identical before and after — the wording moved without a word of it changing.

**Rule-ID convention, with the existing ids grandfathered.** Nothing was renamed: `NY-NR-45` sits in 76 golden receipts, and a receipt is not editable. The argument is that **a rule id is a handle, not a claim** — everything an id is tempted to encode (statute, date, threshold, jurisdiction) already has a correctable home on the rule, and the id does not. All 46 existing ids are exempt by an explicit committed list; 17 would fail the convention today.

### Static assurance

**Z3 static pack verifier.** Per same-priority rule pair: `PROVED-DISJOINT`, `NOT-PROVED` with a concrete witness, or `OUT-OF-FRAGMENT` naming the construct it declined to encode. Also reports uncovered input regions per decision attribute. Across six packs: 25 proved disjoint, one genuine overlap (correct — a registered eNote *is* a promissory note, which is why `PKG-NOTE-31 overrides PKG-NOTE-30`), nine uncovered regions, all intended and now witnessed. It discharges two TILA disjointness claims that previously lived only in code comments, one over a deadline the pack computes with its own calendar.

`validate_pack` is deliberately **not** relaxed, so the kernel's proof set stays small enough to audit by reading. A consequence worth stating: because the validator already refuses any pack with an unproven same-priority overlap, `prove` cannot meet one in a committed pack — its non-zero exit is a differential check between two proof systems, not a routine gate.

**What-if queries** (a v1.2 item, pulled forward). Free one input of a decided case and solve the pack backwards. The contract is that **the solver proposes and the kernel disposes**: every answer is re-adjudicated through the real kernel, extremals are boundary-verified, and a solver/kernel disagreement raises with both artifacts rather than returning an answer. A committed broken encoding proves that guard trips — and proves why answer-checking alone is insufficient, since the kernel *confirms* the wrong date the broken encoding produces. Only the boundary check catches it.

It reuses the verifier's SMT encoding with zero edits; a test asserts class identity so divergence must be deliberate.

### Reference wiring

**OR-Tools closing scheduler**, the first resident of `examples/`. CP-SAT plans sign → fund → record to the earliest feasible dates. Every hard constraint is a table of days an adjudication actually permitted; the only constraints the scheduler writes itself are availability. Each chosen date cites the receipt ids that constrained it.

The demonstration is the funding date: compliance opens **Saturday** 2026-02-21, because Saturdays are business days under the precise § 1026.2(a)(6) calendar — the rule schedulers get wrong — and the wire desk is closed Saturdays, so the plan says Monday. Two constraints, two owners, and the output names which one bound the date. The separation is checked by mutation: move the TILA pack from three business days to five and the plan moves with `schedule.py` untouched.

### Infrastructure

**The marker-gated suites now run.** `linkml`, `z3`, and `docling` tests had never executed in CI — the main job runs `pytest` with no extras and no marker selection, so all three were silently skipped. They now run in their own workflow, path-filtered so a rule-pack PR pays nothing for them, plus every merge to main and a weekly cron. The `linkml` one mattered most: its whole job is checking the ontologies against real tooling, and the hot-path validator would have gone on passing while the files drifted out of spec.

### What this milestone changed about the mental model

Three claims in [the architecture guide](docs/neuro-symbolic-architecture.md) were sharpened by the work rather than merely updated:

- **Pack identity is inside the hashed body**, so two packs are two identities even when they encode the same rules. Equivalence between rulebases is therefore a claim about *decisions*, and has to be tested at that level.
- **Between "reproducible" and "true" sits "internally consistent"** — a property duly could not previously claim, because the validator could only say "I cannot prove these disjoint," which is a statement about the validator rather than the rules.
- **"Keep actions outside the kernel" is only half a boundary.** An integration can respect it perfectly at the API level and still hold a second copy of the rule ten lines away, invisible at the seam because the seam still looks correct. It is detectable only by mutation.

And one distinction the contribution work forced: **a rule pack has two halves.** The deciding half reaches the receipt and is frozen. The speaking half — the question, the phrasing — is authored by the same expert in the same file and must never enter a hashed body, because a wording improvement that invalidated 351 receipts would make the wording unimprovable. Governance and identity are not the same boundary.

## v0.3.0 — M3: extraction and review

Extraction adapter protocol with a Docling implementation, content-addressed run envelopes, pack-level abstention policy with confidence floors, the review queue, and calibration mathematics (deliberately unfitted — labels arrive from review). Human corrections re-enter as first-class facts and auto-become golden regression cases. Six rule packs across insurance and mortgage closing.

## v0.2.0 — M2: replay and regression

Append-only bitemporal fact store, the replay verifier, the golden corpus, and rule-change impact analysis wired into CI.

## v0.1.0 — M0/M1: the contract and the first vertical slice

The grounded-fact and decision-receipt specs, JSON Schemas, the rule IR, the reference kernel, the audit-report renderer, and the interactive demo.
