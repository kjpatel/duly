# Changelog

What each release turned out to mean. The [roadmap](README.md#roadmap) says what is planned and what is done; this file says what was learned doing it — the boundaries that moved, the claims that were corrected, and the things that could not be done honestly.

Entries are written after the fact, from merged work.

**These versions are git tags marking milestones, not package releases.** `pyproject.toml` deliberately stays at `0.0.1`: nothing is published, and [installable distribution](README.md#roadmap) is an M5 item. A tag says "this milestone is done and here is what it meant" — it does not say the contract is stable. The fact, receipt, and IR contracts are v0 and may break until v1.0.

## Unreleased — M5

**Rule studio.** A second surface on the demo server (`/rules`) for the rules rather than the documents: every pack rendered as one decision-table grid per concluded attribute, editable as cells, rule forms or YAML, with the kernel's validator, the pack's declared `expected.yaml` cases, an ad-hoc case built by changing input values, golden-corpus impact analysis and the solver all running over one in-memory draft. Drafts are session-only and never written into `rulepacks/` — the same rule as the golden-case export, for the same reason.

*The composition was the contribution, not the tooling.* M4's exit criterion — a domain author can create, validate, test, and impact-assess a rule change without touching the kernel — was already met, by five separate command-line tools an author had to know existed. Putting them in one rail, in the order that catches things, is what let two of them visibly disagree: change New York's 45-day minimum to 60 and all four declared cases pass while the corpus reports one flipped decision. "Declared outcomes catch a pack that breaks, only the corpus catches a pack whose meaning moved" was already written down; the studio is where you watch it happen.

*Building an editor found a third half of a rule pack.* The architecture doc had carefully separated the pack's **deciding** half (hashed, frozen, replayed) from its **speaking** half (phrasing, deliberately never hashed). Neither accounts for the prose: `DEMO-SYNTHETIC` on an invented window, `TODO(verify)` naming what was unconfirmed, the `MODELING BOUNDARY` header, the comment saying whether an `overrides` is a legal exception or a workaround. Strip every comment from a pack and validation passes, all 351 receipts replay byte-for-byte, and impact reports zero — the honest-labeling invariant lives entirely in a layer nothing checks. Any tool that re-emits a pack from the IR destroys it while leaving both governed halves provably intact. The response was neither to forbid the re-emission nor to call it lossless: the studio shows a normalised diff for *what you changed* beside the raw file diff for *what you would be committing*, and keeps a text path that preserves comments.

*One silent bug, found by the round-trip guard rather than by a test.* `duly_dmn.emit.emit_pack` emitted a fixed `pack`/`decisions`/`rules` allow-list — correct for every pack the compiler produces, and silently lossy for a hand-written one, dropping `abstentionPolicy` and `calendars`. A draft missing an abstention policy validates, adjudicates, and answers differently. It now emits every top-level key in input order, handles floats (a quoted `"0.9"` confidence floor is a string the kernel rejects), and the studio asserts `yaml.safe_load(emit(pack)) == pack` before storing any draft. The DMN compilation is byte-unchanged.

Also: `impact.analyze` gained `pack_overrides`, so a candidate pack that exists only in memory can be measured against the corpus — an impact number the author sees *before* writing the file is the only one that can change their mind. `emit_pack` gained a `header` parameter so a non-DMN generator can say how it generated a pack, with a test that a replaced header moves no byte of the body.

**Evidence browser.** A surface on the demo server (`/evidence`) for the evidence rather than the answer: every document a case holds — the committed source bytes beside the extractor's rendition — and every fact ever asserted about it, each with its grounding, provenance, confidence method and calibration reference, content hash, ontology slot, supersession chain, and which of the pack's questions cite it. Above all of it, a knowledge-time dial whose stops are the moments the case's knowledge actually changed.

*The store had been bitemporal since M2 and nothing showed it.* The decision workspace shows the facts a receipt cited — the right frame for reading a decision, and one that structurally cannot show a fact no rule needed or a fact that is no longer true. Dragging the dial back past a reviewer's correction makes the corrected fact not-yet-known, returns the below-floor machine fact it superseded to live, and moves the citations with them. Nothing new is stored to make that work; it is the same event log projected at a different horizon, which is the point.

*Immutability is usually defended as preservation, and preservation is the weaker half.* An append-only log admits two queries: *which facts bind at this horizon* — what adjudication needs, and what `as_of` answers — and *what became of this fact*, which adjudication never asks and an auditor asks first. A mutating store answers neither honestly; a store with a deletion-free log and only a survivor projection answers the first and merely promises the second, which is where duly had been. "Nothing is lost" becomes checkable at the point something reads the history back, not in the schema, which a system can satisfy perfectly while remaining unable to say what it used to believe. So the browser recomputes liveness from the log rather than calling `as_of`, and a test walks every case at every point on its timeline requiring the two projections to agree — a differential check, in the same spirit as `prove` standing behind the pack validator. One implementation answering both questions would have proved nothing.

*The document turned out to have two faces, and only one of them can carry a highlight.* A fact's grounding cites the source document's SHA-256 — the bytes — and a character span into a *rendition*, one extractor's reading of those bytes. The browser serves both and reports whether the file on disk still hashes to what the facts cite, but it draws spans only on the rendition: character offsets are not page coordinates, and an overlay computed from them would be a guess wearing the costume of provenance. The same discipline covers two facts quoting overlapping text — the browser names the span it could not draw instead of dropping it. `Rendition` is now a row in the architecture doc's artifact table, which it should have been all along.

*One refusal and one gap, both stated rather than papered over.* Without the session fact store there is no event log, so the timeline is reported as *absent* rather than rendered with a single stop implying knowledge never changed. And a fact retracted without replacement is unreachable from any live fact through the store's public API, so it does not appear — nothing in the demo retracts, and reaching around the API would have been the worse trade.

**Receipt viewer.** A surface on the demo server (`/receipt`) for a receipt that already exists: the 351 committed receipts searchable by case id or hash from a picker in the toolbar, any receipt openable by paste or file, rendered as the kernel's own audit report and re-verified on open — its own hash, each pinned fact's content hash, and a full re-adjudication compared byte-for-byte. `duly_kernel.report` gained a third renderer over the section structure the Markdown and PDF already share, so the browser is a new *walk* rather than a second report.

*The corpus proved 351 receipts replay; nobody outside this repository could check one.* That gap is what the viewer closes, and closing it sharpened a claim the architecture doc had been making loosely. Content addressing was described as "mutation is detectable" — true relative to a seal that whoever mutated the document can re-apply. Flip a verdict, recompute `receiptSha256`, and the artifact is consistent again: genuine facts, correct hashes, a well-formed derivation, a report rendering fluent sentences over real statutory citations. Every check that treats the receipt *as a document* passes. Only re-running the rules refuses it. So tamper-evidence and fidelity are different properties, verification is three checks reported separately rather than one verdict, and the middle check must be able to say *not checked* — a receipt pins facts by hash, so one arriving alone genuinely cannot reproduce its own evidence, and passing it would convert an absence into an assurance.

*The second distinction is about standing, not computation.* Golden replay and single-receipt verification run the same kernel over the same inputs and compare the same bytes. What differs is who may conclude something: replay over the corpus is a claim duly makes about artifacts duly produced, checked by CI duly configured. The identical computation, performed by the party holding a receipt against the facts and pack version it names, needs no trust in the producer. A decision record only its author can verify is documentation; one its recipient can verify is a receipt.

*A bug the API tests could not see.* `/inspect` first took receipts and facts as JSON objects, and every genuine fact came back reported as tampered with — only through a real browser. JavaScript has one number type, so a fact's `"score": 1.0` survives `JSON.parse`/`JSON.stringify` as `1`: a different canonical body, a different content hash. Python round-trips it faithfully, which is exactly why a Python-side test suite proved nothing. Content addressing is over bytes, so the endpoint now takes raw JSON *text* and Python does the only parse. Any future surface moving hashed bytes through a browser inherits this.

*One refusal worth naming.* When a receipt's `rulePack.version` no longer matches the file on disk, the viewer does not fall back to it. Rule descriptions from a version the receipt never saw would read as the text its rules carried; the gap is reported as `pack-moved` with both versions, and the rule text is omitted.

**Version scopes.** The receipt's `engine.version` — inside every receipt hash — was `duly_kernel.__version__` by direct import, which made the golden corpus a hostage to the release cadence: publishing the distribution under any new number would have invalidated all 351 receipts without a rule, a fact, or a decision having changed. It is now a pinned constant, `SEMANTICS_VERSION`, naming the kernel's *decision semantics*. The emitted bytes are unchanged; what changed is the dependency.

*Three scopes, nested one way only, and a coincidence that hides the regression.* The distribution moves on any release, the kernel package moves when its code changes, and the semantics version moves when its meaning changes — a semantics change implies a code change implies a release, never the reverse. All three read `0.0.1` today, so re-coupling the sealed field to the package version changes no output, passes every test, and replays the corpus green — until the first release breaks 351 receipts at once, far from the edit that caused it. The guard is therefore behavioural: a test bumps the package version to `1.0.0` and requires a byte-identical receipt. The sealed value is a handle, not a claim, for the same reason `NY-NR-45` keeps its name.

*The procedure got written down where it cannot be missed.* [docs/release-process.md](docs/release-process.md): the version declarations across four scopes and which move for a given change, what counts as breaking per contract — including that the receipt hash covers the whole body, so "additive and backward-compatible" does not exist for receipts — and the discriminator that keeps a semantics rev honest: golden bytes moved with packs and facts unchanged means the kernel's meaning moved. Three decisions are marked PENDING rather than guessed; they resolve in M5's compatibility policy.

**Consumed from outside.** [`examples/minimal-integration`](examples/minimal-integration/) is the whole contract at its smallest: a fictional company's expense policy as its own ontology and its own two-rule-plus-constant pack, three facts, one adjudication, one receipt verified by recomputing its hash — about a hundred lines, none of which import a path inside duly. `check_wheel.sh` builds a wheel, installs it into a clean virtualenv, copies the example somewhere else entirely, and runs it with the source tree off `sys.path`.

*A test that passes inside a repository cannot distinguish a toolkit from a repository with a library-shaped subdirectory.* Inside the checkout every assumption about where files live happens to be true, which is why the example is an instrument and not only a deliverable. Running it from a wheel found four things no suite here could see: content addressing — the first call any integration makes — reachable only as `duly_kernel.receipt`, a module path that reads private; the conformance CLI defaulting `--ontologies` to duly's own directory and raising a traceback rather than a diagnosis when that is wrong; `verify` and `impact` disagreeing about an empty corpus, so an adopter's first CI run fails on the second command they try; and a kernel-only `pip install duly` pulling in a web framework and a PDF library. The committed `receipt.json` is diffed against what the wheel produces, so it proves determinism across *environments* rather than only across runs.

*The gap was wider than the example could reach.* It exercises two packages of nine, so [`.github/scripts/wheel_smoke.py`](.github/scripts/wheel_smoke.py) now touches one real entry point per shipped package from an installed wheel — and immediately found that `duly_review` did not work at all outside this repository. The queue read the grounded-fact schema from a path relative to the *repository*, and `spec/` is in no wheel, so its central operation raised `FileNotFoundError` for every adopter while every test here passed. Known failures in that script are declared with the finding that owns them and fail the run if they start passing, so an entry cannot outlive its bug; fixing that one emptied the list.

*A threshold is a rule, not a number in a guard.* Writing the example's `$200` limit found that the IR has no money literal — money is an amount *and* a currency, and a bare number is only the first — so the limit became its own cited, effective-dated rule bound with `derived:`. That is the better artifact and it is what every committed pack already does: no `when:` guard in this repository contains an inline numeric literal. Chasing it found a real bug in the other direction. A DMN cell reading `> 200` against a money column is the most natural thing a business analyst writes; it is valid S-FEEL, renders to valid duly source, and produces a pack `validate_pack` *accepts*, because the rule IR type-checks nothing at load time. The compiler reported success and the pack died on the first real fact. Given the pinned ontology's value kinds it now refuses that cell by name — but the underlying gap, that pack validation does not type-check expressions at all, is recorded as [rule-IR open question 4](spec/rule-ir.md#open-questions-v0) rather than papered over.

**One canonical form.** `content_hash` was implemented **seven times** across the repository under three signatures, two of them carrying comments reading "must match spec/validate.py exactly" — a copy pinned by a code comment. They are now one implementation in [`duly_core`](core/duly_core/), whose charter is stated in its docstring and deliberately narrow.

*Copies of a function are not independent implementations.* The plan of record had been to keep the seven and add a test asserting they agree. duly's real differential checks compare different *mechanisms* — `prove`'s SMT solving against `validate_pack`'s syntactic matching, the evidence browser's log replay against the store's survivor projection — and seven copies of three identical lines have no algorithmic diversity at all. Such a test proves only that nobody typed it wrong, while borrowing the credibility of a check that does much more, and it crowds out the one that would work.

*The oracle for a canonicalization function is a specification.* [`spec/canonical-vectors.json`](spec/canonical-vectors.json) commits eleven `(document, canonical bytes, digest)` triples, and the property tests re-derive what RFC 8785 requires *independently* of the implementation. Which resolved a claim the schemas had been making loosely: RFC 8785 orders object keys by UTF-16 code unit, Python's `sort_keys` orders by code point, and the two disagree above the BMP. duly said "RFC 8785" and implemented the approximation. Across 1772 committed documents zero have a non-ASCII object key, so implementing the real rule was provably inert — 351 receipts replay byte-for-byte with the sort order changed — and the label became true rather than being weakened. The vectors are also the artifact another language needs: implementing duly's fact contract previously meant working from prose.

*The contract ships.* The three JSON Schemas moved from `spec/` into `duly_core`, because a path relative to a *package* resolves identically in a checkout and in site-packages while a path relative to the *repository* resolves in exactly one of them. Moved rather than copied: two shipped packages read them, and vendoring into one would have recreated the defect `duly_core` exists to remove. That widened a charter written a week earlier as "nothing else, ever" — the amendment and its reasoning sit in the docstring, so the next widening has to argue with a stated position rather than an absence.

**The seams that assumed a repository.** Each toolkit package now takes the paths it reads from its caller. `duly_conformance`'s CLI has no path default at all — pass `--ontologies` or set `DULY_ONTOLOGIES`, and a registry that cannot be loaded is diagnosed with an exit code rather than raised as a stack trace, kept distinct from the exit code for "your facts are wrong" so a CI job can tell a broken registry from a broken corpus. `verify`, `impact` and `generate` shared out three different answers to "what is a case's pack path relative to?" — two of them resolved against duly's own install location — and now share one that tries the working directory and the corpus's parent, naming every candidate when nothing resolves.

*An empty corpus is a state, not a mistake.* `verify` returned 0 on one and `impact` raised, so the two disagreed about identical input. Both now succeed, and both say in words that nothing was measured, because "0 of 0 decisions flip" and "verified 0 cases" are true sentences that read as passes — the trap [rulepacks/README.md](examples/rulepacks/README.md) already documents one level down for a pack with no corpus coverage. A *missing* directory still fails.

*The demo computed the repository four times, and calling it configuration found it was not honest.* `app.py`, `rules_api.py`, `evidence_api.py` and `receipts_api.py` each derived their own `REPO_ROOT` — four copies of the assumption that duly's checkout *is* the content, true exactly once. They now read one `ContentRoots`, defaulting to this repository so `uvicorn demo.app:app` is unchanged and moving together under `DULY_DEMO_CONTENT`. The point was never the environment variable: it made the claim that these surfaces are toolkit rather than teaching content testable, and the first run of that test failed. Pointed at an empty root the demo raised `FileNotFoundError` instead of reporting "no scenarios" — its built-in fixture scenario reads `spec/examples`, so it is content like any other, and a missing *demonstration* was taking the server down. It returns `None` now, and all four pages are verified at 200 with zero items in a real uvicorn process rather than only under `TestClient`, because the failure was at import time.

*The fifth instance, and the sharper form of the lesson.* Four repo-relative paths were fixed before a sweep of every `__main__.py` found a fifth: `duly_whatif`'s CLI resolved a case's pack against its own install location and defaulted `--ontologies` to duly's directory. Its failure mode was worse to diagnose than the others because it was not a failure — a missing registry yields `None` and the tool proceeds with value kinds inferred from use, so an adopter silently got the weaker answer, with a code symbol's domain widened from the permitted values to "the literals this pack mentions plus anything else". That is the quantifier an `UNSATISFIABLE` verdict ranges over, and nothing in the output said so. It does now, from `solve()` rather than the CLI, because a library caller passing `registry=None` is in the same position. Deleting the default then exposed what it had been hiding: some packs cannot be encoded without a registry at all — an attribute the pack never *reads* has no usage to infer a kind from — and that case was escaping as an uncaught `OutOfFragment` traceback where a diagnostic belongs. **A default that is right in this repository hides the wrong-path case and every exception behind it.**

*The corpus generator's templates are example content, and the generator is not.* The six packs, their vocabularies, and the fact builders that speak them are teaching artifacts; the scheduling, seeding, validation and writing around them are the toolkit. `register_kind` and `register_template` make that a seam an adopter can populate for their own packs, and refuse a duplicate name rather than overwriting — a corpus whose contents depend on import order is not reproducible, which is the one property that file exists to provide. The refactor was proved inert by regenerating at the same seed and diffing bytes, and that check immediately caught a transcribed default question that changed 17 cases while the full suite, replay *and* impact analysis all stayed green: the generator had faithfully produced 350 valid cases of the wrong thing.

**A corpus the toolkit owns.** [`fixtures/`](fixtures/README.md) is an invented widget domain — one pack, four cases, committed receipts, one ontology, a deterministic builder — and it exists so duly's own suites stop depending on duly's teaching content. The kernel's suites moved onto it first.

*The rule is one sentence, and it is not about tidiness.* A test that would still pass if its subject were deleted is not a test. `rulepacks/`, `starters/` and `golden/` are example content that M5 relocates under an `examples/` umbrella an adopter can delete, and the claim being tested is that deleting it leaves a working toolkit. A suite pointed at that content cannot check the claim: delete it and the suite does not fail — it stops being collected, or skips, or asserts over an empty glob. All three read exactly like success, which is the worst failure mode a test can have.

*It reached further than tests, which is what made it worth doing early.* [`spec/decision-digest-vectors.json`](spec/decision-digest-vectors.json) — a **contract artifact**, the thing another language implements duly's digest against — was generated from `golden/` receipts. Self-contained, so it would have survived the deletion intact; but the test proving its two "real" receipts are genuinely committed receipts would have quietly stopped meaning anything, and a spec artifact resting on content an adopter is invited to delete is the same category error one layer up. Rebuilt from `fixtures/`.

*The demo's review arc is content now, and removing the hardcoded name uncovered what it was hiding.* `demo/app.py` used to pick its review scenario by literal id — `notice-ny` — in four constants, with the ingest wrapped in `except Exception: pass`. Point the demo at other content and the arc simply did not appear: no error, no log line. Degrading quietly is right for a missing *demonstration*, which is exactly why hardcoding *which* one went unnoticed; the two failures are indistinguishable from outside. A scenario now opts in with a `reviewArc` block in its manifest — the attribute to script below the pack's floor, the confidence, the title — the same way it opts into the stub extractor. This repository's arc is unchanged in every field, which was the check that mattered: the point was to remove a name from toolkit code, not to change what the demo shows.

*And the name was hiding a second dependency.* With it gone, a fixture-only deployment still gets no arc — because the arc lives only in the session store, and store-backed ingest needs extraction *targets* that the fixture scenario does not have. One silent failure was standing in front of another. That is the recurring shape of this phase: a hardcoded path does not merely couple two things, it conceals everything downstream of itself.

*A phrasing guard that matches nothing fails quietly, which is worth a fixture.* Writing the fixture pack's money phrasing, the first guard was `when: { value: "0.00" }` — and a money decision's value is an amount and a currency, not a scalar, so it matched nothing. The demo did not complain: it fell through to the unguarded case and rendered a plausible answer. The correct form is `amount: positive`. The fixture keeps the corrected version with a comment naming the mistake, because a pack author will make it and the failure mode is a verdict that reads fine and came from the wrong branch.

*The two loudest-looking tests were the quietest, and neither showed up as a failure.* Converting the rule studio's suite, the deletion measurement said 29 failures. It was 31. `test_declared_cases_run_green_against_every_committed_pack` looped over a glob of packs, and with the packs deleted the loop body never ran; `test_every_refusal_example_is_reported_not_raised` was `@pytest.mark.parametrize`d over a directory, and parametrize is evaluated at *collection*, so an empty directory produced zero test cases. pytest reports the count that remains and says nothing about what left. Both tests passed. Both were named after claims nothing was checking. The fix in each is one line — assert the glob is non-empty before using it, and loop inside the test rather than parametrizing over the filesystem — and the general form is now in CLAUDE.md, because "asserts over an empty glob" was already written down and these two are the shapes it takes in practice.

*The blast radius of an edit is not a syntactic property of the edit.* The studio shows a diff, a solver-backed equivalence panel and corpus impact side by side, and it is easy to read that as belt-and-braces for careless authors. The fixture pack now makes the real case reproducible: change one derived value from 50 to 70, and all three of the pack's decisions change what they conclude while two of the three rules stay byte-identical on the page — they read the moved value as a `derived` binding, and nothing in their own text, guards, or grid row moves at all. The equivalence panel returns a witness naming a widget scoring exactly 50, the boundary where the two packs part. The diff is complete and honest and it is still not where the effect lives. That is the argument for the panel, and it is stronger than the one the docs had been making.

**The demo became a package.** `demo/` is `duly_demo/`: an `__init__.py`, relative imports between the four surfaces, `static/` shipped as package data, and a tenth entry in `.github/scripts/wheel_smoke.py` that imports `duly_demo.app` from an installed wheel outside the repository. `uvicorn duly_demo.app:app` is the command everywhere it was `uvicorn demo.app:app`; no hashed byte moved, and 1,003 tests pass unchanged.

*"Toolkit, not teaching content" had only ever been tested from one side.* Phase 3 deleted everything around the demo and required it to keep booting. That proves the surfaces do not depend on the *content*; it says nothing about whether they can leave the *repository*, and they could not. Every `from demo import rules_api` resolved because the repository root happened to be on `sys.path` — true in a checkout, true under `uvicorn` started from the root, and false the moment the code lives in site-packages. The generic top-level name would also have collided with any other `demo` an adopter installed. Both are the repo-relative-path defect (A8/A9) wearing a third costume: an import path, not a file read.

*The wheel's most load-bearing demo files are the ones no import statement names.* `static/` is 22 pages, scripts, stylesheets and two fonts, referenced only by a `StaticFiles` mount and by URLs the browser requests. A wheel that shipped the Python and dropped the assets would install cleanly, import cleanly by any test that stops at `import duly_demo`, and fail on the first request. It happens that the mount runs in `app.py`'s module body, so importing the app *is* the assets check — which is why the smoke entry is three lines and still catches the whole failure.

*Rootedness cuts once more, in the other direction.* This is the only package whose directory sits at the repository root rather than inside a component directory, which means it is the only one whose test suite lives *inside* the package. Every other suite is a sibling (`kernel/tests` beside `kernel/duly_kernel`) and could not be swept into a wheel if someone tried. `duly_demo/tests` would have shipped to every adopter by default, along with the agent guidance in `duly_demo/CLAUDE.md`; the wheel target now excludes both, and that exclusion exists for exactly one package for exactly one reason.

*One limitation, named rather than implied.* A green smoke run says `duly_demo` imports and mounts from a wheel. It does not say an installed demo has anything to show. `content.py` still derives its default content root as `Path(__file__).parent.parent / "examples"`, which under site-packages is a directory that does not exist — so an installed demo boots to the built-in `spec/examples` scenario and honest empty listings, which is Phase 3's degrade-honestly behaviour working correctly and is not yet a useful demonstration. Whether the wheel should carry content or the limitation should be documented is a packaging decision, deliberately left to the packaging PR. The distinction is the one `wheel_smoke.py`'s own docstring insists on: a package that passes a smoke test is not thereby a package that works.

**The deletion gate.** The separation claim stopped being a sentence and became a CI job: on every push, `git rm -r examples/` runs, the eleven toolkit suites pass against the deleted tree, the replay verifier's refusal is asserted by exit code *and* message — the missing-directory answer an adopter's deletion actually produces, distinct from the softer `verified 0 cases` an empty corpus earns — and all four demo pages boot against nothing. A claim a repository makes about itself is worth exactly as much as the machinery that would catch it going false.

**The move.** The teaching content lives under `examples/` now — `rulepacks/`, `starters/`, `golden/`, `ontologies/`, and the DMN examples, 2,253 files by pure rename, with `review-0001` and its siblings byte-compared across the boundary. The claim the whole phase was building toward is machine-checked at last: `git rm -r examples/` leaves 791 toolkit tests passing with zero failures, the replay verifier refusing with an honest missing-directory message, and the demo booting to one built-in scenario and empty listings rather than a stack trace.

*The design decision that made 2,253 renames cheap: the content-root contract stayed put.* A demo content root still holds `starters/`, `golden/`, `rulepacks/`, `ontologies/`, `dmn/` directly — what changed is that this repository now offers `examples/` as its default root instead of itself. Nobody adopting duly mirrors this repo's internal nesting; no fixture content root changed shape; and because the five directories moved as *siblings*, the 351 committed case files' `rulePack` references kept resolving through the existing sibling fallback without a single rewrite. The built-in `spec/examples` scenario is the one deliberate behaviour change: it now ships with the demo — pinned to the repository, served under any content root — because the default root no longer contains `spec/`, and the deleted state is better for it: the demo demonstrates the contract's own worked example instead of nothing.

*The deletion simulation out-performed every scout, again.* Two waves of test relocation were planned from readings of the code; the simulation then found 26 more — among them `review/tests`, a 45-failure suite no scout had swept, and `test_generate`, whose whole-file disposition the plan had recorded two PRs earlier and nobody had executed. It also unmasked two things that were never move problems at all: `core/tests` and `whatif/tests` had never been in the main CI suite loop, and whatif's CLI checked for its optional solver *before* validating `--ontologies` — so a typed-but-wrong path was refused as a missing dependency in exactly the venvs CI runs. The measurement keeps finding what reading misses; that is now the standing lesson of this phase, demonstrated four times.

*Every toolkit suite now survives the deletion of the teaching content, and the last two defects were found by measurement, not by reading.* The kernel-report, whatif, DMN and extraction suites moved onto `fixtures/` — four parallel conversions, each classifying what stays as example content in place. Two things no scout's read of the code had caught fell out of the deletion measurement itself: `spec/compatibility_demo.py` — a contract demonstration executed by a kernel test — still read a `golden/` receipt, the same category error the digest vectors had; and `test_rule_ids`' committed-pack sweep half-passed over a deleted directory, two tests failing loudly while two passed over nothing. Also the *seventh* instance of the repo-relative-default defect: `prove-equivalent` kept its `--ontologies` fallback because the sweep that fixed the sixth read files, and this was the second parser in a file whose first was already clean. Sweep by parser, not by file.

*Conversion under an honest corpus is not a rename.* Three of the four suites hit a place where the fixture content could not carry the old assertion, and the resolutions are the interesting part. The report suite found that adjudicating the fixture scenario as committed *abstains* — the below-floor score means empty `inputFacts`, so every converted assertion would have passed vacuously; the existing rehash-a-fact precedent closes it, and the gap it names (no committed fixture case with document-grounded facts) is recorded rather than papered over. The whatif suite proved a doubted twin constructible — freeing the score and demanding not-permitted is UNSAT because the exception needs a category no score can supply — and named the one path with no fixture equivalent (the open code set's residual region) instead of weakening it. And the defeat narration the NY-specific report test had been carrying alone is now asserted on toolkit content, where deleting the example cannot take it.

*The fixture scenario's facts were schema-invalid, and nothing was positioned to say so.* They carried `renditionId` and a `locator` block — a shape no production code reads, violating `DocumentGrounding` three ways — because they were hand-assembled by the fixture builder instead of emitted by the extraction adapter. The conformance gate validates attributes and values, not the envelope around them, and the schema-checking tool globs `starters/`, not `fixtures/`. The fix is structural rather than corrective: the scenario now has a committed *targets* file (`fixtures/targets/`), and its facts are whatever `StubAdapter.extract` emits from it — the same way every real starter is built, with `verify_fact_span` re-checking each quote against the slice it claims. A fixture built by a private code path drifts; a fixture built by the shipped one cannot.

*Sensitivity was only ever hand-written, which meant the redaction path was only ever hand-fed.* The one fact in the repository marked `sensitivity: pii` was the hand-assembled fixture fact — no adapter could produce one, so the report renderer's redaction was reachable only from facts built by code that does not verify spans. Extraction targets now carry the field and `build_fact` passes it through: a *target author* declares handling class, the adapter carries it, and an absent field still means `internal`. Nothing is inferred — an adapter guessing at PII would be asserting a handling class it cannot ground.

*The review arc now proves itself on toolkit content alone.* A fixture-only deployment — `DULY_DEMO_CONTENT` pointing at a content root assembled from `fixtures/` — ingests its scenario into the session store, scripts the below-floor confidence, offers the correction, flips the decision, and exports a golden bundle that skips the seeded `review-0001` and takes `review-0002`. The evidence browser and review-arc suites (22 tests) run against that root; 8 tests remain example-content under deletion and every one is classified in place as moving with `examples/`. One premise did not survive the conversion honestly and was retired rather than forced: "other scenarios carry no abstentions" was a property of `notice-ny`'s clean base case, not of the toolkit — the fixture scenario's own base case abstains organically, and the replacement test asserts the scripted arc and the organic source stay separate, which is the stronger claim.

*A fixture corpus can be too agreeable to be useful.* Every case in `fixtures/` scored either 12 or 80 against a threshold of 50, so any edit to that threshold flipped all three restricted cases at once or none — which meant impact analysis over these fixtures could only ever answer "everything moved", and could not demonstrate the thing it exists for: a pack whose *meaning* moved while every declared outcome stayed green. `fx-0006` scores 60. That is the whole reason it exists, and the bar it clears is a new one for this corpus: not a behaviour that was unreachable, but a *distinction* the corpus could not draw.

*A boolean decision never reaches the machinery that words the answer.* Converting the demo's API suite stopped at once: half its tests assert that verdict wording is **pack data** — `phrasing:` blocks, placeholders, tones — and the fixture pack's only decision was boolean, so it took the kernel's Yes/No fallback and never reached that path. The entire phrasing mechanism was untestable except through the teaching packs, which is precisely the dependency this phase exists to sever. The pack grew a money decision with a phrasing block, and the scenario grew a `sensitivity: pii` fact for the report renderer's redaction path. Growing it is a rebuild rather than an edit — `pack.version` is inside every receipt — and the rebuild found two literals that should always have been derived: a decision-digest vector hardcoding a "later" pack version that the bump made the *current* one, collapsing an equivalence class into its base, and a PROV-O test pinning the pack URN. The equivalence test caught the first, which is the whole reason it checks a relation rather than a table of constants.

*A corpus is not a scenario, and the demo reads scenarios.* The fixture cases ground their facts in attestations, which is honest for synthetic data and leaves the whole span machinery — the evidence browser's highlighting, quotes in the audit report, span verification itself — with nothing to exercise. So the fixtures grew one: a generated PDF, its rendition, and three facts grounded in character spans of that rendition, one below the pack's confidence floor so a review arc has something to resolve and one marked `sensitivity: pii` for the report's redaction path. The spans were *found* in the rendition text rather than typed — a guarantee that has since become the extraction adapter's, which verifies every span it emits (see the fixture-targets entry below).

*Converting the first demo suite found the import-time binding pointing the other way.* The demo binds its content roots at import, which is right for a server — import is startup — and a test suite that points `DULY_DEMO_CONTENT` at a temporary root therefore has to reload the modules *back* when it finishes: `monkeypatch` unsets the variable and un-reloads nothing. Converting one suite turned zero failures into fifty across the rest of the directory until that teardown existed. The receipt viewer's 35 tests now run against a content root assembled from `fixtures/` at test time — `golden/`, `rulepacks/<pack.name>/pack.yaml`, `ontologies/` — rather than a second committed copy of the fixtures in a second layout, which would be two artifacts that must not disagree.

*The deletion gate was measured rather than estimated, and the number changed the plan.* Doing the deletion in a detached worktree and running the toolkit suites against it gives 220 failures and 93 errors across eight suites, against a plan that had estimated "ten files". The count is not the finding. The finding is that it mixes two populations: tests asserting *toolkit* behaviour through example content, which must stay and be repointed at `fixtures/`; and tests whose subject genuinely *is* the example content, which should move under `examples/` and be deleted with it. Most are the second kind — so **the deletion gate cannot pass before the move**, and no quantity of fixture work will get it there. Writing guards to keep those tests alive would be scaffolding for a state the move removes.

*One defect surfaced that is right to fix either way.* `provetest_helpers.py` scanned `rulepacks/` at module scope, so a missing directory was a **collection error**: every test in `test_prove.py` and `test_prove_equivalence.py` stopped existing, including the ones that never touch a pack. `prove` is toolkit and those files stay after the move, so the scan had to tolerate absence. A test that cannot be collected is worse than one that fails — pytest reports the count that remains, and nothing says what left.

*The fixture corpus turned out to be a corpus.* `verify --golden fixtures` replays its four cases, which let the verifier's own suite stop building corpora with `generate` and copy the committed fixtures instead — worth doing on its own terms, since the generator's templates are example content and a verifier test that builds its corpus with them is asserting the verifier through a dependency it does not have. `impact` needed nothing at all: it already owned a `mini-golden` fixture.

*A third instance of the repo-relative path default, found by a sweep that had already been run for it.* `prove`'s `--ontologies` defaulted to `ontologies` — duly's own directory relative to the working directory — exactly as the conformance gate's and what-if's had. It survived the sweep that caught the second because that sweep read every `__main__.py`, and `prove`'s CLI lives in `prove.py`. The lesson is not "sweep harder": **sweep by behaviour, not by filename** — `argparse` calls are where a path default hides, and module names are not. Its failure mode is the mildest of the three and is worth recording as the counter-example: without a registry `prove` already reports `OUT-OF-FRAGMENT` naming the symbol it could not type, so the degradation was loud and the fix needed no equivalent of what-if's absent-registry note. Changing the flag's contract then produced a second, smaller lesson: the sweep for its documented invocations had sixteen hits and was piped through `head`, so ten were read and the two that mattered — the CI workflow and the pack-authoring guide — sat past the cutoff. CI caught the first within a minute. Nothing would ever have caught the second.

*The corpus needed a human correction, which is a useful thing to be forced into.* PROV-O's `wasAttributedTo` and `wasRevisionOf` mappings are unreachable without a human-asserted fact that supersedes a machine one, so the fixtures grew `fx-0004`: `fx-0003` after review, the below-floor score corrected, the abstention answered and the decision flipped — the arc `review-0001` demonstrates, in a form that owes nothing to the insurance starter. Building it also surfaced a distinction the fixtures now encode: the case commits the *post-correction projection*, because supersession is a store-level projection and `adjudicate` is handed a fact list rather than a store.

**The freeze.** [spec/compatibility.md](spec/compatibility.md) states what v1.0 promises, per contract, because the fact, receipt and rule-IR contracts break differently and freezing them is three different acts. The receipt schema is closed and gains no extension point ever — anything that wants to travel with a receipt travels in a separately-hashed sidecar — which closed the three linked open questions that had been waiting on each other: `rulePack.compiledFrom`, declared disjointness proofs, and backend identity. Two claims needed code, and both are inert against the corpus: 351 receipts replay byte-for-byte, `impact` reports 0 of 351 flips.

*"Replay by whom?" was the question nothing had asked.* Every guarantee in this repository ends in "re-adjudicate and compare the bytes", and every one quietly assumed the replaying kernel means by the rules what the sealing kernel meant. Nothing anywhere read `engine.version` — `verify` re-adjudicated all 351 receipts without once checking whose semantics they claimed. That is free while one implementation of one semantics has ever existed, and it stops being free the moment an evaluator bug is fixed: the correction *is* new semantics, and a receipt sealed under the old ones must not reproduce under the new ones or the fix is a lie about what changed. So replay is now scoped to a semantics version, a kernel may implement several, and one meeting a version it does not implement **refuses**. The failure that guard exists for is silent and green: two semantics that differ on some inputs agree on most, so a kernel replaying receipts it has no standing to replay produces a wall of passes.

*Two hashes, because "the same receipt" and "the same decision" are different questions.* `receiptSha256` identifies an artifact; nothing could say two runs had decided the same thing. `decision_digest()` is a pure function over the determinant fields, excluding `caseId`, `rulePack.gitCommit`/`url`, `engine.kernel` and `engine.backend` — everything that identifies the *run* rather than the adjudication. That makes cross-backend equivalence definable, which the architecture doc had listed as a prerequisite for a second backend: `engine.backend` is inside the hashed body, so two backends cannot produce identical bytes, and **two receipts agree when their digests match**. The tempting alternative — lift `engine.backend` out of the hash and let the bytes agree — was rejected because it costs the receipt its answer to what evaluated it. The digest is a function and never a field: one stored inside the body it digests is exactly the extension point the schema refuses.

*New expressive power costs one semantics version.* Quantified bindings ([rule-IR open question 1](spec/rule-ir.md#open-questions-v0)) are deferred past v1.0, and the reasoning generalises past them. A kernel that grows an IR construct the previous version lacked cannot keep claiming that version, because a receipt using it would be stamped with a version whose honest implementations cannot reproduce it. Additive-and-backward-compatible does not exist for a hashed body, and it does not exist for semantics either — which is what turns the deferral from debt into a price. The same reasoning made the envelope's signature affordance unnecessary: a signature inside a hashed body is circular, so it travels in a sidecar and the frozen shape needs no hole for it.

*Two conventions nobody had chosen read exactly like conventions somebody did.* Ten version declarations existed and two had readers; six package `__version__` strings had none, and three packages had already skipped the convention without anyone noticing — which was the diagnosis rather than an inconsistency to tidy up. The six are deleted, `duly_kernel.__version__` stays because it expresses a decision the project actually made, and a test pins the count at one. The rule-pack scheme was in the same state: `2026.3.0` looked like a third revision and is a birth number — no component of any pack version has ever moved. It is now `<content-year>.<substantive>.<clarifying>`, split where the receipt splits, and the third component is the only version rule here whose correctness CI can check (a clarifying bump must show zero flips against a non-empty corpus diff).

*Enforcing it inverted a committed test, which is how you know it was a decision.* `test_outranking_without_supersession` asserted that a non-superseding correction still wins by outranking — and the receipt it produced was the argument against itself: a persistent `low_confidence` entry on `nc:noticeMailedDate` for an attribute the decision *used*. Adapting the test would have been the wrong move; it now asserts the refusal, and a second test keeps the carve-out honest, because C6 binds the queue and not the store. `review-0001` regenerates byte-identically, so the one committed arc was already doing it correctly.

*The design that enforced the review invariant would have broken the one it depends on.* Requiring a `low_confidence` resolution to supersede the fact it rules on had a sketched mechanism — the queue stamps `supersedes` from the entry's own fact id rather than trusting callers. It cannot: a correction arrives content-addressed, so writing a field into it changes its hash and its identity, and the queue would be handing the store a document its author never sealed. The queue refuses and names the required fact id instead. The evidence settled the question faster than the argument did — `review-0001`, the preserved-forever case, already uses the superseding form, and its receipt's `abstentions` array is empty, so the branch that bends this spec's own definition of `abstentions` was exercised by no committed artifact.

## v0.4.0 — M4: standards, authoring, and static assurance

Ten capabilities across twenty-five pull requests (#6–#30), and **the golden corpus was never regenerated once**. All 351 receipts still replay byte-for-byte from before any of it. Every track's acceptance test was that `git diff -- golden/` came back empty.

### Interchange and contract

**PROV-O JSON-LD export.** Facts, receipts, and run envelopes expand to W3C PROV triples under external context files, stored bytes unchanged. The mapping is deliberately partial — bitemporal effective time, confidence, and abstentions have no faithful PROV equivalent and stay in duly's namespace. An earlier "lossless mapping" claim was corrected in the process.

**Ontology conformance gate.** A fact's `schemaRef` resolves against a registry of versioned, immutable LinkML artifacts; a misspelled attribute that previously surfaced only as a rule silently failing to bind now fails ingestion loudly. The hot-path validator interprets a documented LinkML subset rather than importing linkml-runtime, which would drag RDF tooling into the runtime; a marker-gated suite proves the files are genuine LinkML under real tooling.

**Pack-embedded calendars.** `add_business_days` walks a calendar carried inside the rule pack — excluded weekdays, cited holiday dates, and a coverage window that raises rather than guessing past its edge. "Last Monday in May" became legal content, versioned and receipt-pinned with the rules that use it, instead of engine code. The TILA pack now computes the rescission deadline it could previously only certify.

### Authoring

**DMN decision-table compiler.** DMN 1.3+ tables compile into the rule IR; the kernel cannot tell the result from a hand-written pack. Deliberately narrow — S-FEEL cells only, three of seven hit policies, a mandatory citation and effective date on every row. It refuses rather than approximates: an uncited row is a compile error, not an invented `TODO(verify)`.

*The acceptance criterion was unachievable as written.* It demanded a DMN-authored pack produce "the same decision **and receipt**" as its IR equivalent. A receipt pins its pack's name and version, so two packs are two identities and the hashes cannot match. What is proven instead — same decision, same rules fired in the same order, same defeat chains, same input facts — is asserted alongside the difference, which a test pins as precisely as the agreement.

*And the proof is fixture-bounded.* Perturbing a compiled rule from `> disclosed` to `>= disclosed` leaves the whole equivalence suite green, because the two differ only when the amounts are exactly equal and no committed fixture reaches that boundary. A perturbation the fixtures can see fails 10 of 12 tests. This is what motivated pack equivalence in the verifier below.

**Pack-owned decision phrasing.** A decision's verdict wording moved from `demo/app.py` into the pack, alongside the `question` a pack already declared. Every determination the demo can render is byte-identical before and after — the wording moved without a word of it changing.

**Rule-ID convention, with the existing ids grandfathered.** Nothing was renamed: `NY-NR-45` sits in 76 golden receipts, and a receipt is not editable. The argument is that **a rule id is a handle, not a claim** — everything an id is tempted to encode (statute, date, threshold, jurisdiction) already has a correctable home on the rule, and the id does not. All 46 existing ids are exempt by an explicit committed list; 17 would fail the convention today.

### Static assurance

**Z3 static pack verifier.** Per same-priority rule pair: `PROVED-DISJOINT`, `NOT-PROVED` with a concrete witness, or `OUT-OF-FRAGMENT` naming the construct it declined to encode. Also reports uncovered input regions per decision attribute. Across six packs: 25 proved disjoint, one genuine overlap (correct — a registered eNote *is* a promissory note, which is why `PKG-NOTE-31 overrides PKG-NOTE-30`), nine uncovered regions, all intended and now witnessed. It discharges two TILA disjointness claims that previously lived only in code comments, one over a deadline the pack computes with its own calendar.

`validate_pack` is deliberately **not** relaxed, so the kernel's proof set stays small enough to audit by reading. A consequence worth stating: because the validator already refuses any pack with an unproven same-priority overlap, `prove` cannot meet one in a committed pack — its non-zero exit is a differential check between two proof systems, not a routine gate.

**What-if queries** (a v1.2 item, pulled forward). Free one input of a decided case and solve the pack backwards. The contract is that **the solver proposes and the kernel disposes**: every answer is re-adjudicated through the real kernel, extremals are boundary-verified, and a solver/kernel disagreement raises with both artifacts rather than returning an answer. A committed broken encoding proves that guard trips — and proves why answer-checking alone is insufficient, since the kernel *confirms* the wrong date the broken encoding produces. Only the boundary check catches it.

It reuses the verifier's SMT encoding with zero edits; a test asserts class identity so divergence must be deliberate.

### Reference wiring

**OR-Tools closing scheduler**, the first resident of `examples/`. CP-SAT plans sign → fund → record to the earliest feasible dates. Every hard constraint is a table of days an adjudication actually permitted; the only constraints the scheduler writes itself are availability. Each chosen date cites the receipt ids that constrained it.

The demonstration is the funding date: compliance opens **Saturday** 2026-02-21, because Saturdays are business days under the precise § 1026.2(a)(6) calendar — the rule schedulers get wrong — and the wire desk is closed Saturdays, so the plan says Monday. Two constraints, two owners, and the output names which one bound the date. The separation is checked by mutation: move the TILA pack from three business days to five and the plan moves with `schedule.py` untouched.

### Infrastructure

**The marker-gated suites now run.** `linkml`, `z3`, and `docling` tests had never executed in CI — the main job runs `pytest` with no extras and no marker selection, so all three were silently skipped. They now run in their own workflow, path-filtered so a rule-pack PR pays nothing for them, plus every merge to main and a weekly cron. The `linkml` one mattered most: its whole job is checking the ontologies against real tooling, and the hot-path validator would have gone on passing while the files drifted out of spec.

### What this milestone changed about the mental model

Three claims in [the architecture guide](docs/neuro-symbolic-architecture.md) were sharpened by the work rather than merely updated:

- **Pack identity is inside the hashed body**, so two packs are two identities even when they encode the same rules. Equivalence between rulebases is therefore a claim about *decisions*, and has to be tested at that level.
- **Between "reproducible" and "true" sits "internally consistent"** — a property duly could not previously claim, because the validator could only say "I cannot prove these disjoint," which is a statement about the validator rather than the rules.
- **"Keep actions outside the kernel" is only half a boundary.** An integration can respect it perfectly at the API level and still hold a second copy of the rule ten lines away, invisible at the seam because the seam still looks correct. It is detectable only by mutation.

And one distinction the contribution work forced: **a rule pack has two halves.** The deciding half reaches the receipt and is frozen. The speaking half — the question, the phrasing — is authored by the same expert in the same file and must never enter a hashed body, because a wording improvement that invalidated 351 receipts would make the wording unimprovable. Governance and identity are not the same boundary.
