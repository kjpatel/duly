# Working on duly_demo/

Loaded alongside the root CLAUDE.md when work touches this directory. These
are the demo surfaces' gotchas — every one has actually bitten. The root
file's invariants and conventions still apply; its "Demo discipline" and
"One shape per job" conventions are the design rules, these are the traps.

This directory is an installable package (`duly_demo`, listed in the wheel's
`packages`), not a loose script directory that happens to import from the repo
root. Two consequences. The four surfaces reach each other with *relative*
imports (`from . import rules_api`), so nothing here depends on the repository
being on `sys.path`. And `static/` ships in the wheel as package data — the
mount in `app.py`'s module body raises when it is absent, which is precisely
the failure `.github/scripts/wheel_smoke.py`'s `duly_demo` check catches.

- **Shipping in the wheel makes `content.py`'s default root wrong, and it is wrong quietly.** `REPO_ROOT = Path(__file__).resolve().parent.parent` is still the duly checkout's root *here* and is site-packages *there*, so `DEFAULT_ROOT = REPO_ROOT / "examples"` names a directory an installed demo does not have. Nothing raises: the surfaces are built to report an absent root honestly, so a wheel-installed demo serves the built-in `spec/examples` scenario and empty listings — the degrade-honestly discipline doing exactly its job, and the reason nobody notices the demo has no content. Consolidating four per-module `REPO_ROOT`s into one did not fix this; it made one copy of the assumption instead of four. This is the same defect the root CLAUDE.md's "a path relative to a *package* resolves everywhere" gotcha names, and it is the **settled posture**, not an open question: the wheel deliberately carries no content, an installed deployment sets `DULY_DEMO_CONTENT` (the adopter's guide says so at the point it matters), and the built-in `spec/examples` scenario is the one thing that ships. Do not "fix" it by widening the fallback: a demo that silently finds *some* directory is worse than one that finds none.

- **The studio's decision tables are a projection, and re-emission drops the arguing part.** `duly_demo/rules_api.py` renders packs as DMN-shaped grids using the *kernel's* expression parser (`duly_kernel.expr.parse` + a Var walk) — never a second parser, and never a DMN decompiler, because `duly_dmn` is one-way on purpose. Two consequences when you touch it. A guard referencing more than one binding belongs in the row's `cross` list, not in a column; flattening it into a cell would misstate the rule. And a structured edit re-emits the pack through `duly_dmn.emit.emit_pack`, which is byte-deterministic but carries no comments — so `DEMO-SYNTHETIC`, `TODO(verify)` and `MODELING BOUNDARY` headers are lost, and *nothing* catches it: validation passes, replay is byte-identical, impact reports zero. That is why the studio shows a normalised diff and the raw file diff side by side and keeps a lossless YAML-text path. `emit_pack` emits every top-level key in input order for the same reason — it used to emit a fixed `pack/decisions/rules` allow-list, which silently dropped `abstentionPolicy` and `calendars` from any hand-written pack it round-tripped.

- **JavaScript's JSON silently breaks content addressing, and the symptom accuses the wrong party.** JS has one number type, so `JSON.parse`/`JSON.stringify` turns a fact's `"score": 1.0` into `1` — a different canonical body, a different `contentHash`. A browser that parses a receipt and posts it back as an object is asking the server to verify a document nobody emitted, and the server dutifully reports *every* genuine fact as tampered with. So `/api/receipts/inspect` takes raw JSON **text**, one blob per pasted box or chosen file, and Python does the only parse (`_parse_documents`); the server sorts receipts from facts by which field each carries, so no caller ever has to re-serialize to fit a shape. Any future surface that moves hashed bytes through the browser inherits this: move the text, never the object. Python round-trips `1.0` faithfully, which is why the API tests only caught it once they went through the real page. **The rule is directionless, and the download half went unnoticed for longer than the upload half** — the workspace's "Receipt JSON" button built its own file with `JSON.stringify(state.receipt)`, which is the identical defect pointed outward: `abstentions[].confidence.score` and `.threshold.minConfidence` are `"type": "number"` in the receipt schema, so a receipt whose abstention scored exactly `1.0` downloaded as `1` and failed its own hash check in the viewer next door. Every export is a server round trip now (`/api/report?format=receipt|bundle`), and `test_the_workspace_exports_a_receipt_the_viewer_can_verify` pins it by feeding the download straight back into `/inspect`. Nothing caught it before because the committed scenarios' floors and scores are not integral — the bug needed a `0.0` or a `1.0` to appear, and honest demo data never produced one.

- **The fixture scenario's facts are display-adjusted copies, and do not hash to their own ids.** `_load_fixture_scenario` reads the committed `spec/examples` facts and rewrites `grounding.charSpan` to point into `FIXTURE_RENDITIONS` — the abridged text the demo actually serves — because the committed spans index the full rendition, which the demo does not ship. Correct for a highlight, and a mutation of a content-addressed body: recompute `contentHash` on one of those in-memory facts and it does not match. Nothing noticed for as long as the demo only *displayed* them; the bundle export is the first path that hands facts to somebody as hashed artifacts, and it refuses rather than emit a file whose facts check fails, because "the evidence has been altered" is indistinguishable from a forgery on the receiving end. The guard is on the artifact (re-hash every pinned fact before emitting) rather than on the code path, so any future edit-on-the-way-through is caught the same way. If a surface ever needs *both*, keep the pristine fact beside the display copy — do not un-rewrite the span, which is how the committed spans would end up pointing into the wrong text.

- **The evidence browser recomputes liveness on purpose, and `duly_demo/tests/test_api.py` forces fixture mode on everyone.** `duly_demo/evidence_api.py` replays the store's event log instead of calling `FactStore.as_of`, because as_of answers "which facts survive" and a browser also has to show the ones that did not — superseded, retracted, not-yet-known. The two projections must agree, and `test_the_browsers_projection_is_the_stores` walks every case at every point on its timeline asserting they do; keep them as separate implementations or that test becomes a tautology. Two more things bite. Its fact universe is seeded from the far-future `as_of` and walked through supersession chains, so a fact retracted *without* replacement is unreachable — nothing in the demo retracts, and the alternative is reaching past the store's public API. And `duly_demo/tests/test_api.py` sets `DULY_DEMO_FORCE_FIXTURE=1` at **import** time, process-wide, so any store-backed demo suite must `monkeypatch.delenv` it and reset the runtime or it will pass alone and fail in the directory run. **The same binding cuts the other way, and is easier to miss:** a suite that points `DULY_DEMO_CONTENT` at a temp root must reload the demo modules *back* on teardown, because `monkeypatch` unsets the variable and un-reloads nothing — converting one suite to a fixture content root turned 0 failures into 50 across the rest of the directory until that teardown existed. Call [`demotest_helpers.reload_demo()`](tests/demotest_helpers.py) on both sides rather than writing the reload out: it was copied into a second suite once, which is one copy short of the version that gets edited wrong. The same module is where a corpus becomes a content root — three path rewrites (`case.yaml`'s pack, `expected.yaml`'s `factsFrom`, the scenario's `rulePack`) plus two placements (the extraction targets, a seeded `review-0001`), and the two families fail differently: a skipped rewrite offers an empty list, a missing targets dir removes the review arc entirely. All five are silent.

- **A receipt viewer is three checks, and only one of them needs the repository.** `duly_demo/receipts_api.py` reports hash, fact-integrity and replay separately because a forged receipt that was *re-sealed* passes the first two — the interesting case, and the one a single "valid/invalid" pill would hide. Three consequences when you touch it. Never collapse the checks into one verdict field: `partial` (inputs unavailable) and `fail` (a check refuted) are different answers, and standalone receipts are the normal case, not the degraded one. Never fall back to the pack now on disk when `rulePack.version` has moved — the module returns `pack-moved` and omits rule text instead, because descriptions from a version the receipt never saw would read as the text its rules carried. And never import `duly_kernel` at module scope here: it is the one surface that can do nothing without the kernel, which is exactly what makes a top-level import tempting, and `duly_demo/app.py` includes this router unconditionally — so that import takes *all four pages* down when the kernel is absent, instead of this one reporting "not checked". It reaches through `_kernel(name)` for the same reason every kernel reach in `app.py` is lazy. Two things also arrive as caller data on `/inspect` and must be treated as such: `rulePack.name` (validated against a pack-name pattern, and no longer joined into a path at all — see below), and the receipt bytes themselves (see the JSON-fidelity gotcha above).

- **A receipt names its pack; it does not name a directory.** `_resolve_pack` used to build `rulepacks/<rulePack.name>/pack.yaml` and look there. That is true of duly's own six packs and of nothing else: `pack.name` is a declaration inside the file, the directory is where somebody put it, and no schema, kernel check or receipt field ties them together. An adopter who named the directory anything else got `replay: unavailable` — the answer that reads as *a missing pack* rather than as *a lookup that could never have succeeded*, which is why it survived every test here. Resolution is now **discovery**: glob `rulepacks/*/pack.yaml`, read each file's declared `pack.name`, match on that, and prefer the candidate whose version the receipt was produced by. The pack-name pattern stays as a cheap "that cannot name a pack" rejection, but it is no longer guarding a path join. Do not add a cache in front of the glob — `_INDEX` caches an immutable corpus, whereas a pack file is the one thing here somebody edits mid-session.

- **The demo's review arc is content, and it is store-only.** A scenario opts in with a `reviewArc` block in its manifest (attribute to script below the floor, confidence, title, case id) — `duly_demo/app.py` names no scenario, having previously hardcoded `notice-ny` in four constants. Two things still bite. The arc exists **only** in the session store, so a deployment whose scenarios cannot be store-ingested has none — and store ingest needs extraction *targets* under `starters/tools/targets` (the index key is the `documentId` **field inside** each file; the filename is convention). The fixtures carry their own (`fixtures/targets/`, placed by `build_content_root`), so a fixture deployment produces the arc — and the fixture scenario's facts are what the adapter emits from that targets file, because the hand-assembled first version was schema-invalid and nothing was positioned to notice. And `_ingest_review_case` is wrapped in `except Exception: pass`, so every one of those failures is silent by design: right for a missing demonstration, and the reason a missing *arc* tells you nothing about why.
